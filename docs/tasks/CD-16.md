# CD-16 — Stage 1 diagnostics integration and race tests

- Status: Not started
- Stage: 1
- Estimate: 4 h
- Dependencies: CD-05…CD-15
- Plan: [code-diagnostics.md](../plan/code-diagnostics.md)

## Goal

Prove the Stage 1 checker-to-UI flow for findings, empty results, failure,
cancellation, dirty drafts, output caps, and stale event races with deterministic tests.

## Grounding in current code

- Frontend tests run with Node's test runner through `frontend/test/resolver.mjs`.
- `helpers.mjs` compiles real Svelte stores/components with explicit dependency substitutions.
- `file-editor.test.mjs` uses real CodeMirror state with a DOM-free EditorView stand-in.
- SSR component rendering tests output, not client effects, focus, or physical scrolling.
- Existing draft/save/action tests cover host identity, late replies, conflicts, and guards.
- Backend seams are the planned codediagnostics manager, engine/App, and RPC layers.

## Concrete steps

1. Reuse sanitized CD-04 adapter fixtures and CD-01 contract/race fixtures.
   Add deterministic fake process/event schedules; do not require installed checkers.
2. Build a small fixture project with contained Go/Svelte roots, an unopened file,
   Unicode/CRLF content, a dirty draft, and an out-of-root diagnostic attempt.
3. Exercise approved explicit run through adapter/supervisor/manager and transport;
   assert normalized provider sets, coverage, run identity, and replacement behavior.
4. Feed equivalent snapshots/events to the real CD-10 store with mocked API boundaries.
   Render controls, panel, picker, and source against that state; probe editor lint separately.
5. Verify successful findings are not failures and a successful empty rerun removes
   only the replaced provider's old findings, including badge/panel/marker changes.
6. Verify failed/canceled runs retain old findings marked stale and cannot clear
   another provider's results. Cover tool missing and independently available adapters.
7. Schedule superseded run completion, initial snapshot after a newer event, duplicate
   batches, sequence gaps/resnapshot, old generations, and same path on a different host.
8. Assert old results cannot replace new results after reconnect, revoke, root switch,
   cancellation, or detach. Ensure event listeners/process ownership are cleaned up.
9. Check project/output/message/stderr/frame caps and partial/truncation signaling.
   Use negotiated CD-01/CD-09 limits; do not freeze unvalidated proposed defaults in UI tests.
10. Run checks while a draft is dirty and while save outcome is uncertain; assert
    no implicit writes, no draft replacement, and no saved-file inline markers on the draft.
11. Confirm exact deduplication and source attribution agree across summary, folder/file
    badges, filtered panel, source, and editor for the same eligible findings.
12. Keep this a focused suite over existing seams; split/re-estimate before coding
    if a new full browser or transport test framework would exceed four hours.

## Contract and security considerations

- Final operation/event APIs come from CD-01; all currently proposed names are provisional.
- Existing `provider.Diagnostics` / `Backend.Diagnostics()` remains unchanged and independently tested.
- Test unauthorized roots, traversal/absolute/URI escapes, symlink boundary cases,
  and out-of-root findings represented only as provider status.
- Inject HTML-like messages and bounded stderr with secrets; assert escaped output,
  no body/protocol logs, and no automatic result persistence/telemetry.
- Unapproved open, missing tools, old remote capabilities, and revoked grants must not execute.
- Tests never install tools, invoke project scripts, or contact external services.

## Focused test matrix

| Scenario | Required observation |
|---|---|
| Findings then empty success | Atomic provider replacement and all views clear |
| Failure/cancel after findings | Old set retained stale; no fresh-success claim |
| Dirty/uncertain draft | Text/undo retained; no writes or saved-file overlays |
| Cap or sequence gap | Visible partial/resync state; no silent success |
| Superseded run/host/generation | Late payload rejected in manager and store |
| Old remote or missing one adapter | Browsing/editing works; availability stays explicit |
| Revocation/disconnect | Owned work stops and late publications are invalid |

## Acceptance checklist
