# CD-11 — Approval controls and project-check status

- Status: Not started
- Stage: 1
- Estimate: 3 h
- Dependencies: CD-10
- Plan: [code-diagnostics.md](../plan/code-diagnostics.md)

## Goal

Provide approval controls, Check/Cancel/Retry actions, provider availability,
summary counts, and honest coverage status without delaying Go to File opening.
Stage 1 runs checks only after an explicit Check Project action.

## Grounding in current code

- `GoToFileDialog.svelte` remains mounted and uses a hidden backdrop when closed.
- Its open transition resets the picker and focuses the search input.
- Project context comes from `files.dir` and `link.dataHost`; host labels are display only.
- `link.blockedReason` already gates host-dependent actions.
- Header, picker, viewer, presentation mode, and close guards must remain usable.

## Concrete steps

1. Consume the separate CD-10 code-diagnostics store; do not duplicate its state machine.
2. Bind attachment visibility/context to dialog open, directory, and backend identity.
   Reuse CD-10 lifecycle operations and avoid double attachment from reactive effects.
3. Render the dialog immediately; discover configurations and reconcile status asynchronously.
4. Add “Enable code checks for this project” with the CD-02 approval explanation.
5. Offer Enable for this session, Always allow this project, and Not now.
   Present the actual host/root scope, not just the root button's friendly label.
6. Offer revocation through the approved-state controls and stop showing actionable
   run controls immediately when approval is revoked or context changes.
7. Show Check Project only for supported, approved contexts with an available checker.
   Disable/coalesce duplicate requests through the store rather than starting local work.
8. Show Cancel for active project checks and Retry for the specific failed provider.
   Keep successful findings distinct from provider failure or cancellation.
9. Render disabled, approval required, unsupported, tool missing, starting, checking,
   idle, partial, failed, disconnected, and stale states with meaningful text.
10. Show error/warning totals from shared selectors alongside provider scope and
    “saved files”; retain partial/truncated/stale qualifiers when results remain visible.
11. Use “No reported problems” for zero findings, never an unconditional “all clean”.
12. Keep controls keyboard accessible, label busy states, and use restrained live announcements.
    Preserve search focus on open and existing Escape, prompt, tab, and close behavior.

## Contract and security considerations

- All operation/event names and shapes remain provisional until CD-01 is finalized.
- Code diagnostics are distinct from existing `provider.Diagnostics` / `Backend.Diagnostics()`.
- UI approval is not authorization: backend directory authorization and execution grants remain required.
- Explain plugins/config execution, possible dependency/network/cache activity, and no sandbox guarantee.
- Never install tools, invoke package scripts, save drafts, or auto-run checks on open/save.
- Render messages/status as text; never persist findings, document bodies, or protocol traffic.
- Hide unsupported remote controls without breaking file browsing or editing.

## Focused tests and manual checks

- Fixture-render every state above; assert action presence, disabled rules, and coverage labels.
- Mock approve/run/cancel/retry/revoke; assert correct context and no execution on open or Not now.
- Switch host/root during an approval or run request; old completion cannot update current controls.

- Manually tab through controls; verify search autofocus, Escape lock, prompts, and presentation mode.
- Run frontend `npm test` and `npm run check`; SSR tests alone do not prove focus behavior.
