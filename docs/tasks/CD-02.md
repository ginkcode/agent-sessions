# CD-02 — Project execution trust, grants, and path authorization

- **Status:** ✅ Done
- **Stage:** 1 — Project checks
- **Estimate:** 4 h
- **Dependencies:** CD-01
- **Plan:** [code-diagnostics.md](../plan/code-diagnostics.md)

## Goal

Implement explicit execution approval independently of directory browsing
permission, using the finalized [CD-01](CD-01.md) contract. Define the exact trust
fingerprint and approval copy before any automatic execution can be introduced.

## Current code grounding

- `Service.knownDirectory` in `internal/engine/service.go` checks catalog CWD and
  RepoRoot using cleaned paths; it is not an execution grant or canonical identity.
- `internal/files/edit_path.go` resolves roots and rejects traversal/link targets
  for editing; inspect this policy but do not mistake it for checker sandboxing.
- `internal/app/remote.go` distinguishes selected remote connections from Local;
  display labels alone cannot safely identify an approved host.

## Concrete implementation steps

1. Adopt CD-01 identity and error shapes. Specify stable host identities for
   Local, SSH, and WSL, including reconnect, changed endpoint identity, and aliases.
   Decide grant storage ownership across local UI and host-side authorization.
2. Define canonical-root resolution on the project host after known-directory
   authorization. Specify symlink aliases, case handling, missing roots, and
   Windows drive/UNC semantics without widening a subdirectory to its parent.
3. Define and document a bounded fingerprint: approved executable identity and
   relevant adapter configuration inputs, versioning, invalidation triggers,
   local binaries, and fail-closed behavior when identity cannot be verified.
4. Provide grant operations for session-only approval, explicit persistent approval,
   denial, lookup, and revocation using CD-01 contracts. Persist only Always allow
   records; select a narrowly scoped durable storage location and schema.
5. Scope session grants to the owning connection/app lifetime. Design cancellation
   hooks for the future supervisor/manager so revocation invalidates generations
   and stops work promptly, including checks waiting in a queue.
6. Revalidate root/grant/fingerprint immediately before execution; separate safe
   metadata discovery from version probes or configuration evaluation that execute
   code. Require renewed approval on relevant identity changes.
7. Validate diagnostic paths/URIs independently of tool trust. Reject traversal,
   wrong host/scheme, and symlink escapes; turn out-of-root findings into bounded
   provider status rather than navigable links or file-content reads.
8. Specify approval UX text and state transitions for CD-11: Enable for this
   session, Always allow this project, Not now, and revoke/reapproval feedback.
   Implement backend policy now; do not build the dialog controls in this task.

## Contract and security considerations

- Follow CD-01; do not overload `provider.Diagnostics` or scanner health state.
- Explain that tools/plugins may read dependencies, use networks, or write caches:
  fixed argv and root containment are not a sandbox or no-write guarantee.
- Persist grants only, not document bodies, raw tool output, or diagnostic results.
- Define behavior for root/config changes between preflight and process start;
  acknowledge limits of pathname-based checks rather than promising isolation.

## Focused tests

- Session grant expiry, persistent reload, denial, revoke, corrupt grant records,
  fingerprint mismatch, and same path on two different hosts.
- Catalog-unknown root, nested root, symlink alias/escape, `..`, absolute paths,
  malicious file URI, platform path cases, and no out-of-root content access.
- Fake cancellation observer verifies revoke invalidates pending/running work.
