## Goal

Implement svelte-check detection and parsing using CD-03 execution and CD-04
fixtures. Follow finalized [CD-01](CD-01.md) contracts and report missing tools,
dependencies, unsupported configuration, and partial package coverage honestly.

## Current code grounding

- `frontend/package.json` declares Svelte 5, svelte-check ^4.7.6, and TypeScript;
  its check script passes `--tsconfig ./tsconfig.json`.
- The backend root and frontend package are distinct scopes in this repository.
  Detecting only the selected root's package.json would miss this frontend.
- Package scripts are not an execution API: the application must not run `npm run
  check` or `npx` to reproduce this repository's development workflow.

## Concrete implementation steps

1. Read CD-01 through CD-04 decisions relevant to the adapter; use only formats,
   modes, and versions validated by CD-04. Split/re-estimate before production
   parsing if version differences or platform launch behavior exceed this scope.
2. Detect contained candidate Svelte packages via bounded metadata reads, with
   deterministic traversal/exclusions and no evaluation of config during discovery.
   Support root and nested packages without walking above the authorized root.
3. Declare supported package/config layouts and coverage; handle multiple packages,
   discovery caps, missing tsconfig/configuration, and dependency references outside
   the root without silently claiming full-project checking.
4. Discover installed executables/runtime on the project host per CD-04. Validate
   project-local binaries under CD-02 approval; handle Windows launchers through a
   verified direct argv strategy, not an interpolated shell command.
5. Distinguish missing svelte-check, missing Node/dependencies, unsupported versions,
   unsupported project, and configuration/tool failure. Never install a package,
   execute a package script, or download a fallback tool.
6. Build verified fixed argv/cwd and invoke CD-03, serializing package runs under
   its project limit. Configuration identity must match the approved fingerprint.
7. Parse machine output and summaries from fixtures; normalize messages, optional
   code/source, severity, path, optional ranges, and saved-file freshness. Do not
   mistake banner/summary/progress records for diagnostics.
8. Convert evidenced location units to zero-based UTF-16 exclusive ranges; validate
   malformed/negative/out-of-bounds locations and use file-level results where
   precision is absent. Reject out-of-root links and bound messages/read sizes.
9. Return complete/partial/failure outcomes for CD-07 replacement semantics, including
   mixed package success/failure, malformed output, and resource caps. An empty
   parse after failure is not a successful empty provider replacement.

## Contract and security considerations

- Follow CD-01 and keep code results separate from `provider.Diagnostics`.
- Svelte configuration/plugins can execute code; approval is required even for
  installed project-local tools. Fixed argv is not a sandbox.
- Results describe saved files under declared configuration, not unsaved drafts
  or every TypeScript/Svelte file in the repository.
- Do not log raw stdout/config/source or persist diagnostic text automatically.

## Focused tests

- CD-04 fixture tables: warning/error, clean, accepted diagnostic exit, tool and

- Package trees: frontend nested under Go root, multiple packages, no Svelte,
  missing runtime, unsupported version, symlink escape, and discovery limits.
- Unicode/non-BMP and CRLF ranges, unsafe paths/messages, partial multi-package
  outcomes, and exact argv; fake runner keeps tests independent of Node installs.
