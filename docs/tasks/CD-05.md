## Goal

Implement a go vet adapter using CD-03's supervisor and CD-04's verified formats.
Follow finalized [CD-01](CD-01.md) contracts, preserving the distinction between
saved-file findings, unavailable tooling, operational failure, and partial scope.

## Current code grounding

- This repository's backend module is declared in root `go.mod` (Go 1.26.8).
- `internal/engine/service.go` authorizes catalog directories; adapter discovery
  must not expand a selected CWD to a convenient parent module/repository.
- Existing Go tooling declarations do not establish runtime availability on Local,
  SSH, or WSL hosts. Execution must use the tools installed on the project host.

## Concrete implementation steps

1. Read CD-01 contracts, CD-02 policy, CD-03 execution seam, and CD-04 version and
   invocation decision. Do not invent parser fields or assume all Go exits mean
   the same thing. Re-estimate before coding if spike evidence changed scope.
2. Detect Go modules/configuration using bounded metadata traversal wholly within
   the authorized root. Handle nested modules deterministically, excluded paths,
   symlink escapes, and discovery limits; report skipped scope as partial.
3. Define coverage per discovered module/package selection. Decide how workspace
   configuration and parent modules affect invocation without silently adding
   out-of-root analysis roots; surface unsupported layouts explicitly.
4. Resolve the approved installed Go executable on that host and validate version
   using the approved supervisor path. Report missing/unsupported tools separately
   from unsupported projects or build errors; prevent implicit toolchain installs.
5. Build only the fixed argv/cwd verified in CD-04. Schedule contained modules
   through the supervisor's one-process-per-project policy; do not create a second
   unbounded pool inside the adapter.
6. Parse the verified stream/format and exit behavior from fixtures. Normalize
   project-relative paths, source/code, severity, message, optional ranges, and
   saved-file freshness according to CD-01.
7. Convert tool positions using the evidenced coordinate units and bounded saved
   source reads when needed. Preserve file-level findings; do not fabricate an
   accurate end range or column when the tool only supplies a coarse location.
8. Validate every emitted path and range; map out-of-root or malformed output to
   bounded provider status. Handle parse/output/finding caps with explicit partial
   status rather than silently returning an empty successful result.
9. Return a complete provider outcome for CD-07 atomic replacement. Define how
   mixed module success/failure is represented under CD-01; never clear previous
   findings by presenting an incomplete run as a complete clean scan.

## Contract and security considerations

- Approval covers executable/configuration identity; metadata detection alone
  does not authorize a subprocess or execute `go env`/version/config evaluation.
- Go vet analyzes saved files only. Never save a draft or decorate a changed
  draft as if its text matches a disk result.
- Explain go vet is not comprehensive linting; package/build tags and toolchain
  context constrain coverage. Do not label all unreported Go files clean.
- Keep output/results in memory and messages untrusted; no raw-output logging.

## Focused tests

- Table-driven CD-04 fixtures: findings, empty success, build/tool failure,
  malformed/truncated output, version rejection, and accepted nonzero exits.
- Temporary module trees: nested modules, unknown root, parent-only module,
  symlink/out-of-root paths, discovery cap, and spaces/platform path forms.
- Unicode/CRLF conversion, absent ranges, bounded reads, cancellation, and mixed
  module outcome; use fake execution, not the developer's installed Go binary.
