# CD-04 — Verify checker formats and supported-version fixtures

- **Status:** Done
- **Stage:** 1 — Project checks
- **Estimate:** 3 h
- **Dependencies:** CD-01
- **Plan:** [code-diagnostics.md](../plan/code-diagnostics.md)

## Goal

Produce evidence for production go vet and svelte-check adapters: sanitized
output/exit fixtures, fixed invocation choices, and explicit supported-version
decisions. Follow [CD-01](CD-01.md); this is a spike, not production execution.

## Current code grounding

- Root `go.mod` declares Go 1.26.8 and tool directives; version probing must not
  accidentally trigger a toolchain download in the eventual application.
- `frontend/package.json` declares `svelte-check` ^4.7.6 and TypeScript ^5.6.3.
  Its `check` script uses `svelte-check --tsconfig ./tsconfig.json`.
- That script is evidence of repository configuration, not permission to run
  package scripts from the application. Production invocation must be direct.
- There is no existing code-diagnostics adapter or parser to preserve.

## Concrete implementation steps

1. Read CD-01 range, result, coverage, and failure semantics. List evidence needed
   by CD-05/CD-06, keeping tool-specific names/flags provisional until verified.
2. Inventory already installed Go, Node, and svelte-check versions in an isolated,
   intentionally approved fixture workspace. Do not install/download tools or
   execute arbitrary repository configuration just to collect sample output.
3. Verify go vet output modes available on selected installed versions, exact
   argv, stdout/stderr placement, exit statuses, position units, analyzer names,
   multiline messages, and build/package failures versus analyzer findings.
4. Verify svelte-check machine-readable modes and relevant flags for selected
   installed versions: summary records, file/range/severity/code/source fields,
   malformed configuration, missing dependencies, and exit behavior with findings.
5. Capture zero-findings, warning/error, multiple-file, file-level/missing-range,
   malformed-output, and failure cases. Include Unicode/non-BMP, CRLF, spaces in
   paths, and platform path samples where evidence is available.
6. Record every fixture's tool version, argv, cwd layout, stream, exit code,
   provenance, and expected normalized interpretation under CD-01.
7. Sanitize absolute user paths, source excerpts/secrets, and machine details;
   retain enough context to test path conversion and parser ambiguity reliably.
8. Decide supported versions and unsupported-version behavior, direct executable
   discovery candidates, coverage claims, and monorepo/root-detection constraints.
   Missing tools are evidence gaps/unavailable, never simulated successful spikes.
9. Document unresolved cases and re-estimate/split CD-05/CD-06 before coding if
   required parsing or version support cannot fit their plan estimates.

## Contract and security considerations

- This task depends only on CD-01, not the production grant service; manually
  approved isolated experiments must not become an application trust bypass.
- Never use `npx` downloads, implicit installs, or arbitrary package scripts.
- Prefer installed host tools; disclose unavailable platform/version coverage.
- Tool findings and operational failures need distinct evidence, not assumptions
  based solely on exit code. All code diagnostics remain distinct from providers.

## Focused tests

- Validate fixture metadata and JSON where applicable; record expected parser
  assertions for CD-05/CD-06 rather than prematurely implementing parsers.
- Ensure fixtures cover empty success, accepted diagnostic exits, failure,
  malformed/truncated output, and byte/code-point to UTF-16 conversion examples.
- Verify sanitized fixtures contain no personal absolute roots or secret content.
