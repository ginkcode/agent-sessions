## Contract and security considerations

- Local/SSH/WSL servers execute on the project host, not through frontend tunneling.
- Require known-directory authorization and CD-02 trust/fingerprint approval;
  Svelte configuration/plugins and project-local binaries can execute project code.
- Approval is not sandboxing or a promise that toolchains never write/network.
- Bound discovery, diagnostic batches/messages, stdio framing, and request handling.
- Use CD-19 allowlisted configuration replies; deny applyEdit, server commands,
  arbitrary file reads, and workspace expansion outside the authorized root.
- Validate real/virtual URIs; out-of-root findings become status, not navigable links.
- No body/raw protocol persistence or automatic diagnostic telemetry.
- Require push support; pull-only versions and unverified virtual mappings are unsupported.

## Focused tests and manual QA

- Mixed Svelte/TS package fixtures verify ownership, reuse, attribution, and no
  duplicate open/change/close streams or folder-count inflation.
- Cover template/script/style diagnostics, Unicode/CRLF, empty clears, unknown
  virtual URIs, wrong versions, unversioned pushes, and missing dependencies.
- Fake server attempts unsafe requests and oversized/hostile messages; verify denial
  and bounded partial/failure status without source edits or HTML interpretation.
- Approved real-server smoke test edits/fixes an unsaved Svelte error and switches
  view/editor/tabs, confirming correct source selection and retained undo/draft state.
